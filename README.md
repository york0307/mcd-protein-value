## 核心思路：一个 join

营养数据里**没有价格**，菜单里**没有营养成分**。
把 `list-nutrition-foods` 和 `query-meals` 按餐品编码 join 起来，才第一次得出
「每元蛋白质」「每 100 大卡蛋白质」这类**任何单一数据源都不存在的指标**。

这是本项目非用 MCP 不可的原因 —— 而且价格随门店和时段浮动，静态抓取的数据会过期。

## 四项指标

| 指标 | 公式 | 谁该看 |
|---|---|---|
| 蛋白质性价比 | 蛋白质(g) ÷ 价格(元) | 增肌 / 健身 |
| **蛋白密度** | 蛋白质(g) ÷ 能量(kcal) × 100 | **减脂** |
| 热量性价比 | 能量(kcal) ÷ 价格(元) | 预算有限 |
| 钠负荷 | 钠(mg) ÷ 2000mg | 所有人 |

综合评分 `= 0.40×归一(蛋白密度) + 0.35×归一(蛋白质性价比) + 0.25×(1−归一(钠))`，钠是惩罚项。
归一化用样本内 min-max，所以是**相对排序**，不是营养评级。


## 关于样本量

营养库覆盖全时段 160 款（含早餐），门店菜单是当前时段在售的 124 款
（其中 43 款套餐与周边会被排除）。两者按名称精确匹配后通常得 **20 款左右**。

这不是 bug —— 下午三点拉不到早餐数据是正常的。
程序**宁可少收录也不错配**，原因见下。

### 为什么不做模糊匹配

实测踩过两个坑：

- 营养库「吉士汉堡包」会模糊命中菜单「吉士汉堡包**套餐**」→ 价格从单品变成套餐价
- 「大杯玉米杯」和「小杯玉米杯」会同时命中菜单「玉米杯」→ 两个规格拿到同一个价

所以匹配规则是**双向唯一**才采纳：先精确匹配，再去规格修饰后匹配
（`中薯条`→`薯条`、`麦乐鸡5块`→`麦乐鸡`），且要求该菜单名**只被一个**营养条目命中。
「薯条」同时被大/中/小/迷你四个规格命中 → 全部放弃。

同理设了**蛋白 ≥ 5g 准入门槛**：13kcal 的浓缩咖啡（蛋白 1g）密度能到 7.7，
不设门槛会被它霸榜 —— 咖啡本来就不是蛋白质来源。

## 合规说明

- 只调用 `query-nearby-stores`、`list-nutrition-foods`、`query-meals` 三个**只读** Tool，不下单、不领券、不消耗积分。

- 仓库不含任何真实 Token，配置仅用环境变量占位符。
